# 🕒 JavaScript Dates & Time Zones
### Revision Notes for a JavaScript Developer (1 YOE)

**Goal:** Understand UTC, IANA time zones, JavaScript `Date`, `Intl.DateTimeFormat`, and Day.js well enough to handle dates confidently in production applications.

---

# 1. The Big Picture: Why Do We Need UTC?

Imagine a passenger books a flight departing Karachi at **2:00 PM on October 24, 2026**.

Your application has customers in Pakistan, London, and New York. All of them need to understand when that flight departs.

The problem: the same moment has different local clock readings in different locations.

### The solution: UTC

**UTC (Coordinated Universal Time)** is the international reference time standard used to coordinate time worldwide.

Think of UTC as a common timeline shared by computers around the world.

For our flight:

| Representation | Date and time |
|---|---|
| Karachi departure time | October 24, 2026, 2:00 PM |
| UTC departure time | October 24, 2026, 9:00 AM |
| London time at that same instant | October 24, 2026, 10:00 AM |

Why?

- Karachi is UTC+5.
- London is UTC+1 on October 24, 2026, because British Summer Time is in effect.

**Calculation:**

Karachi → UTC:

`2:00 PM − 5 hours = 9:00 AM UTC`

UTC → London:

`9:00 AM + 1 hour = 10:00 AM London time`

All three represent the **same instant**.

### 🧠 Memory trick

- **UTC:** The common reference.
- **Time zone:** The rules for converting between the reference and a location's local clock.
- **Local time:** What the person sees on their clock.

### Why use UTC in applications?

1. Compare events occurring in different countries.
2. Calculate elapsed time accurately.
3. Sort events chronologically.
4. Store timestamps consistently.
5. Exchange timestamps between frontend, backend, and external APIs.

**GOTCHA:** UTC does not mean every date in your application should be converted to UTC. A birthday, for example, is a calendar date—not necessarily a specific instant.

---

# 2. GMT vs UTC: What Should a Developer Know?

- **UTC:** The modern international time standard.
- **GMT:** Greenwich Mean Time, a historical time standard also used for UK winter time.

For ordinary programming, they often display the same clock time when used as a zero-offset reference. Technically, they are different standards.

**Practical rule:** Use UTC for timestamps representing exact instants.

Example:

`2026-10-24T09:00:00.000Z`

The `Z` means the timestamp is expressed in UTC.

---

# 3. What Is an IANA Time Zone?

An IANA time-zone identifier names a region whose time-zone rules are maintained in the IANA Time Zone Database.

Examples:

```text
Asia/Karachi
Europe/London
America/New_York
Asia/Dubai
```

Why not simply use `UTC+5`?

Because a location's UTC offset can change over time.

For example, London uses:

- UTC+0 during GMT.
- UTC+1 during British Summer Time.

If you hardcode London as UTC+0, your application will display incorrect times during British Summer Time.

Using `Europe/London` lets the runtime apply the applicable time-zone rules for the date.

### Important distinction

An offset is a number, such as `+05:00`.

A time zone is a set of rules, such as `Asia/Karachi`.

**GOTCHA:** Never assume a country's time-zone offset will remain unchanged forever. Governments can change time-zone rules.

# 4. JavaScript's Date Object: The Essential Concept

A JavaScript `Date` represents an instant in time, internally measured in milliseconds relative to the Unix epoch.

It does not store a named time zone such as `Asia/Karachi`.

Consider:

```javascript
const flight = new Date("2026-10-24T09:00:00.000Z");
```

This represents one specific instant.

You can display it in different time zones without changing that instant.

```javascript
console.log(flight.toISOString());
```

Output:

```text
2026-10-24T09:00:00.000Z
```

This always produces a UTC representation.

Now display the same instant in Karachi:

```javascript
console.log(
  flight.toLocaleString("en-PK", {
    timeZone: "Asia/Karachi"
  })
);
```

The result represents 2:00 PM in Karachi.

Display it in London:

```javascript
console.log(
  flight.toLocaleString("en-GB", {
    timeZone: "Europe/London"
  })
);
```

The result represents 10:00 AM in London.

### 🧠 Remember

**One instant, multiple representations.**

Formatting a `Date` in another time zone does not change the underlying instant.

# 5. Ready-to-Run Code: Native Date + Intl

Save this as `flight-time.js` and run:

`node flight-time.js`

No external libraries are required.

```javascript
// ==========================================
// FLIGHT TIME: KARACHI -> LONDON
// Date: October 24, 2026
// ==========================================

// The flight departs Karachi at 2:00 PM.
// Karachi is UTC+05:00.
//
// Therefore:
// 14:00 Karachi - 5 hours = 09:00 UTC.

const departure = new Date("2026-10-24T09:00:00.000Z");

// Named IANA time zones.
const KARACHI = "Asia/Karachi";
const LONDON = "Europe/London";

// 1. The canonical UTC representation.
console.log("UTC:", departure.toISOString());

// 2. Display the same instant in Karachi.
const karachiTime = new Intl.DateTimeFormat("en-PK", {
  dateStyle: "medium",
  timeStyle: "short",
  timeZone: KARACHI
}).format(departure);

console.log("Karachi:", karachiTime);

// 3. Display the same instant in London.
const londonTime = new Intl.DateTimeFormat("en-GB", {
  dateStyle: "medium",
  timeStyle: "short",
  timeZone: LONDON
}).format(departure);

console.log("London:", londonTime);

// 4. Display the same instant in New York.
const newYorkTime = new Intl.DateTimeFormat("en-US", {
  dateStyle: "medium",
  timeStyle: "short",
  timeZone: "America/New_York"
}).format(departure);

console.log("New York:", newYorkTime);

// 5. Calculate the current instant.
const now = new Date();

console.log("Current UTC instant:", now.toISOString());

// 6. Display the current instant in Pakistan.
console.log(
  "Current Pakistan time:",
  new Intl.DateTimeFormat("en-PK", {
    dateStyle: "medium",
    timeStyle: "short",
    timeZone: KARACHI
  }).format(now)
);
```

### Expected results for the flight

Your exact punctuation and date formatting may vary by runtime.

```text
UTC:     2026-10-24T09:00:00.000Z
Karachi: 24 Oct 2026, 2:00 pm
London:  24 Oct 2026, 10:00
New York: 24 Oct 2026, 5:00 am
```

The New York result reflects daylight-saving time on that date.

### What should you understand from this code?

- `new Date(...)` creates the instant.
- `toISOString()` represents it in UTC.
- `Intl.DateTimeFormat` formats it for a locale and time zone.
- `timeZone` determines which location's time-zone rules are used.
- The locale controls presentation conventions, such as date ordering and 12-hour versus 24-hour time.

**ASIDE:** A locale is not a time zone. `"en-PK"` controls formatting conventions; `"Asia/Karachi"` controls the time-zone rules.

# 6. Converting Local Time to UTC: A Different Problem

So far, we've started with a UTC timestamp and displayed it in other time zones.

But what if the user enters:

```text
October 24, 2026
2:00 PM
Asia/Karachi
```

Now you need to interpret a local date-time in a specific time zone.

You cannot safely assume that this works:

```javascript
const departure = new Date("2026-10-24T14:00:00");
```

There is no time-zone indicator in that string. JavaScript interprets it as a local date-time in the runtime's configured time zone.

That runtime might not use Karachi time.

Also, do not append `Z` to the input:

```javascript
// WRONG if the input means 2 PM in Karachi.
new Date("2026-10-24T14:00:00Z");
```

That would mean 2:00 PM UTC—not 2:00 PM in Karachi.

### Correct mental model

If the user supplies a local date-time, you need:

1. The local date.
2. The local time.
3. The intended IANA time zone.

Then resolve that combination to an instant.

For production applications, use a time-zone-aware library or a suitable Temporal implementation.

# 7. Day.js: Converting Between Time Zones

Day.js is a lightweight JavaScript date library.

Install it:

```bash
npm install dayjs
```

The UTC and Timezone plugins are required for the following examples.

Save this as `flight-dayjs.js` and run:

`node flight-dayjs.js`

```javascript
const dayjs = require("dayjs");

const utc = require("dayjs/plugin/utc");
const timezone = require("dayjs/plugin/timezone");

dayjs.extend(utc);
dayjs.extend(timezone);

// ==========================================
// EXAMPLE 1: LOCAL KARACHI TIME -> UTC
// ==========================================

const departure = dayjs.tz(
  "2026-10-24 14:00",
  "Asia/Karachi"
);

console.log("UTC:", departure.toISOString());

// Expected:
// 2026-10-24T09:00:00.000Z


// ==========================================
// EXAMPLE 2: SAME INSTANT IN KARACHI
// ==========================================

console.log(
  "Karachi:",
  departure.tz("Asia/Karachi").format("DD MMM YYYY, hh:mm A")
);

// Expected:
// 24 Oct 2026, 02:00 PM


// ==========================================
// EXAMPLE 3: SAME INSTANT IN LONDON
// ==========================================

console.log(
  "London:",
  departure.tz("Europe/London").format("DD MMM YYYY, HH:mm")
);

// Expected:
// 24 Oct 2026, 10:00


// ==========================================
// EXAMPLE 4: SAME INSTANT IN NEW YORK
// ==========================================

console.log(
  "New York:",
  departure.tz("America/New_York").format("DD MMM YYYY, hh:mm A")
);

// Expected:
// 24 Oct 2026, 05:00 AM


// ==========================================
// EXAMPLE 5: CURRENT INSTANT
// ==========================================

const now = dayjs();

console.log("Current UTC:", now.toISOString());

console.log(
  "Current Pakistan time:",
  now.tz("Asia/Karachi").format("DD MMM YYYY, hh:mm A")
);
```

### The most important Day.js distinction

These two expressions perform different operations:

```javascript
dayjs.tz("2026-10-24 14:00", "Asia/Karachi");
```

Interpret the supplied wall-clock time as Karachi time.

```javascript
departure.tz("Europe/London");
```

Convert an existing instant to London's local representation.

**GOTCHA:** Don't confuse interpreting a local time with converting an existing instant. They are different operations.

Also, Day.js does not automatically solve every scheduling problem. Local times can be ambiguous or nonexistent around daylight-saving transitions. Validate inputs and define explicit business rules for those cases.

# 8. What Should a MERN Developer Store in MongoDB?

Suppose you are building a flight-booking application.

A simplified flight record might contain:

```javascript
{
  flightNumber: "PK-501",

  departure: {
    airport: "KHI",
    timeZone: "Asia/Karachi",
    scheduledAt: ISODate("2026-10-24T09:00:00.000Z")
  },

  arrival: {
    airport: "LHR",
    timeZone: "Europe/London",
    scheduledAt: ISODate("2026-10-24T17:00:00.000Z")
  }
}
```

The values are illustrative, not actual airline schedule data.

MongoDB's BSON Date type stores the instant as milliseconds since the Unix epoch.

The application also preserves the airport's time zone so it can display the correct local time.

A real airline system may additionally preserve the original local scheduled date-time and handle schedule revisions.

### Recommended responsibilities

**React**
- Collect user input.
- Display dates in the appropriate time zone.
- Avoid assuming the browser's time zone is the business's time zone.

**Node.js / Express**
- Validate inputs.
- Interpret local date-times in the intended time zone.
- Calculate durations using instants.
- Apply booking and scheduling rules.

**MongoDB**
- Store exact instants using BSON Date.
- Preserve the relevant time-zone identifier when the business meaning requires it.
- Store calendar dates separately when they represent dates rather than instants.

# 9. GOTCHAS Worth Remembering

### GOTCHA 1: A date-only string is not the same as a local date-time

```javascript
new Date("2026-10-24");
```

JavaScript interprets this standardized date-only form as UTC midnight.

But:

```javascript
new Date("2026-10-24T00:00:00");
```

This date-time without an offset is interpreted as midnight in the runtime's local time zone.

That difference can cause bugs.

### GOTCHA 2: Never compare formatted date strings to calculate durations

Bad approach:

```javascript
// Don't calculate durations by comparing display strings.
```

Better approach:

```javascript
const durationMs = arrival.getTime() - departure.getTime();
```

Both values must represent correctly resolved instants.

### GOTCHA 3: UTC offsets can vary by date

London's offset is not always +1. Named time zones account for the applicable rules.

### GOTCHA 4: Midnight conversions can change the calendar date

An instant near midnight in UTC might fall on the previous or following calendar day in another location.

Always format the instant in the intended time zone before presenting its local date.

### GOTCHA 5: Future schedules need special care

If a business says, "Schedule this meeting at 9 AM London time," the intended local time may matter more than today's UTC conversion.

If time-zone rules change before the meeting, the application may need to recalculate the instant according to the business's scheduling policy.

### GOTCHA 6: The server's time zone is not the business's time zone

A Node.js server can run in UTC while serving customers in Pakistan, London, and New York.

Don't rely on the server's default local time zone for business logic.

# 10. What a JavaScript Developer With 1 YOE Should Know

You should be comfortable with the following:

- Creating dates using `new Date()`.
- Understanding ISO 8601 timestamps and the `Z` suffix.
- Using `toISOString()` to obtain a UTC representation.
- Using `getTime()` to compare instants.
- Formatting dates using `Intl.DateTimeFormat`.
- Understanding the difference between a locale, a UTC offset, and an IANA time zone.
- Converting existing instants using named time zones.
- Parsing local date-times correctly with a suitable library.
- Understanding that calendar dates and instants are different data types conceptually.
- Handling daylight-saving transitions when accepting local scheduling input.
- Avoiding assumptions about the browser's or server's local time zone.
- Writing tests for date boundaries, time-zone conversions, and daylight-saving transitions.

You don't need to memorize every time zone. You need to understand which information your application has and which operation it needs to perform.

# 11. Quick Revision Cheat Sheet

| Need | Recommended tool |
|---|---|
| Get the current instant | `new Date()` |
| Represent an instant in UTC | `date.toISOString()` |
| Get epoch milliseconds | `date.getTime()` |
| Format an instant for a time zone | `Intl.DateTimeFormat` |
| Convert an existing instant to another time zone with Day.js | `date.tz("Europe/London")` |
| Interpret local date-time in an IANA time zone with Day.js | `dayjs.tz(localDateTime, timeZone)` |
| Calculate elapsed time | Subtract epoch milliseconds |
| Store an exact instant in MongoDB | BSON Date |
| Preserve a future event's intended local time | Store the local date-time and named time zone as needed |

## The golden rule

**Store instants consistently. Preserve time-zone meaning. Interpret local input correctly. Format for the intended audience.**

## Final takeaway

When you encounter a date in a real application, ask yourself:

**"Do I have an instant, a local date-time, or a calendar date?"**

Then ask:

**"Which time zone gives this value its meaning?"**

Answer those two questions correctly, and most JavaScript date problems become much easier to reason about.
